STATUS — #1 shipped. reducer.ts (the only Critical, and the only one that violates a core hard rule) has been disbanded — see its card. Approach correction: the plan below first said "one reducer file per system folder"; on inspection many cases are cross-cutting orchestration (MOVE_OR_MERGE touches board+merge+battle, FULFILL_ORDER touches orders+board+battle+gear+map), so scattering them into pure system folders would force system→system imports and break the dependency direction. The dogmatically-correct split keeps them as cohesive slices inside the Store module (src/game/store/), which the architecture already designates as the orchestration home. Parity was guaranteed by moving each case body verbatim into a handler keyed by its exact action.type, verified: all 45 actions handled once (no missing / extra / dupes), tsc + vite build + game-config:validate green.

#2–#4 deliberately NOT done. They are view/FX-layer organizational splits — no core-rule violation, and their functional parity can only be confirmed by live visual / touch-gesture testing. Refactoring a subtle gesture SM or a visual VFX hub on faith would risk silent regressions for tidiness, which the "completely maintain functional parity" mandate forbids. They remain available to do with live verification if wanted.

1reducer.ts✓ Done643 → ~30 LOC combinator
Shipped — split into 7 store-local slices (reducer-shell/board/orders/combat/gacha/heroes/gear.ts) + reducer-helpers.ts; reducer.ts is now a ~30-line combinator merging the handler maps and routing by action.type. Public surface (reducer/initState/buildBattle) unchanged. All 45 actions verified handled once; build + config gates green.

Why it was the worst

One switch (action.type) owns state transitions for every system in the game. It's the single most-depended-on sim file, it directly violates module-per-folder (board/orders/combat/gacha/heroes/gear logic all live here, not in their folders), and no system's transitions can be unit-tested without loading the whole tree.

Discipline — each case body moves verbatim (pure (state,action)→state), so it's behaviour-preserving. Each slice gets its own headless unit test. Gate: npm run build + the determinism / auto-play harness (identical action sequence → identical state).
Bonus win — this is the change that makes the codebase actually obey module-per-folder for game logic; every system README then documents its own reducer.

4FxLayer.jsxHigh656 LOC · ~15 handlers

Why

One component that both subscribes to every combat signal and implements every VFX handler inline: handleHeroAttacks · handleLimitCharge · handleOrderChest · handleWaveClear · handleLevelComplete · handleLimitBreak · handleGachaReveal · handleEnemyAttacks plus the DOM primitives flashChip · deathDust · shakeArena · telegraphChip · flashCard · pulseLimitBar · spawnNumber · combo · battleCenter. Adding a VFX means growing this file; the handlers never need React.

VFX god-hub15 handlersDOM primitives inline

Disband → handler registry + DOM-FX toolkit

  1. → fx/handlers/<event>.js — one file per handler, pure (event, ctx) where ctx = the DOM refs/layers it needs
  2. → fx/dom-fx.js — the shared primitives (flashChip/deathDust/shakeArena/telegraphChip/spawnNumber/combo/…)
  3. → fx/handlers/index.js — a {signal → handler} registry map
  4. → FxLayer.jsx becomes a thin subscriber: on mount, wire each signal to its handler from the registry; unsubscribe on unmount. Target < 120 LOC.
Gate: npm run build + visual smoke that each effect still fires (hero attack telegraph, limit break, wave/level clear, order chest, gacha reveal).
