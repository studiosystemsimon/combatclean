Combat Clean — FTUE mockup

The first-run experience as a flexible layer of OVERRIDES + FLAGS on top of gameplay — every number below is the live config. Toggle the layer off and the game runs exactly as normal, with no residue.

MOCKUP · numerically accurate · not wired

1The layer model — how it detaches from gameplay

Gameplay never contains tutorial logic. Instead, each system exposes a tiny read-hook: "is there an FTUE override for this decision? use it — else take the normal path." The FTUE is a config object + a set of persisted flags. Turn it off (or delete it) and every hook falls through to vanilla gameplay.

GAMEPLAY CORE (untouched)

Pure sim — reducer, buildWave, rollOrder, gacha. No if (ftue) branches beyond the read-hooks.
buildWave(level)rollOrder()Gacha.pull() initState() boardlimitEnergy
▲ reads override / ▼ nothing flows back

FTUE LAYER (opt-in, removable)

One config of overrides + a flag set. Lives outside src/game logic; consumed only through the hooks.
enemyCounts[]firstOrder = potion firstPullHeroboardSeed flags.seen.*flags.ftueFirstPull
flags.ftueActive — flip to false → all hooks fall through → pure gameplay, zero code change.

The read-hook pattern (illustrative — every override is the same shape):

// each gameplay decision checks the layer first, then falls through — the ONLY ftue-aware lines.
buildWave(level)      → count = ftue?.enemyCounts[level] ?? formula(level)         // 1,1,2,2,3,3,3,4,5 vs base 3+1/5lvl
rollOrder(firstEver) → reward = ftue.on && !flags.seen.firstOrder ? 'potion' : rollReward()
summon(bannerId)     → hero   = flags.ftueFirstPull ? ftue.firstPullHero : Gacha.pull(...)  // then clear the flag
initState()          → board  = flags.ftueActive ? ftue.boardSeed : normalSeed()

// REMOVE THE FTUE: set flags.ftueActive=false (or drop the config). Every line above takes the
// right branch automatically. No gameplay file changes, no dangling references.

2The override + flag registry

Overrides — active only while the layer is on

  • enemyCounts — per zone-1 level: [1,1,2,2,3,3,3,4,5] (L10 = boss). Overrides buildWave's formula + the rest count-cap.
  • firstEnemies — L1 & L2 pinned to two distinct archetypes (teach one at a time) instead of a random pool pick.
  • firstOrder — the opening order forced to Limit Potion (reward:'potion'), request = exactly the tile the guided forge+merge makes.
  • boardSeed — the guided opening board (which generators + seed tiles + which cells).
  • firstPullHero — the predetermined pre-boss pull (a fixed hero ref, not a roll). hero TBD.

Flags — persisted, one-shot, on the account

  • ftueActive — master switch. false → the whole layer is inert.
  • seen.<beat> — each beat fires once, then records itself (forge, merge, potion, limitBreak, energy, map, summon…).
  • ftueFirstPull — armed at the pre-boss gate; consumed by the predetermined pull, then cleared → later pulls roll normally.
  • specialOrders — stays locked through the FTUE; unlocked later (already wired: flags.specialOrders).
Why this shape: the layer touches gameplay at ~4 read-hooks and nothing else. Designers tune the ramp / potion / pull by editing the FTUE config (data). QA disables the whole tutorial with one flag. Shipping without an FTUE = don't include the config. No parallel tutorial renderer, no forked reward path — the Limit Potion & the predetermined pull are just values the existing systems already accept (potion is a real order-reward; the pull just needs a forced-hero branch).
