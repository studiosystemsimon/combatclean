Hero-Class & Loadout Architecture

One cohesive HeroClass template — stats, progression, abilities, loadout, and look — that code references as a single structure; and a HeroInstance saved on the player's account holding each owned hero's actual state. Plus the generic modular slot system the class declares as “things equipped on / acting on me”. Existing → proposed → sense check → open questions. Nothing implemented — for review + iteration.
The model in one line. HeroClass = the stateless template (the definition — read-only, shared by every copy). HeroInstance = the stateful account item (this player's owned copy: level, ascension, rolled rarity, equipped loadout), pointing at its class. The class owns a loadout of typed slots; each slot holds a modifier that acts on the hero — gear is the first modifier type.

0 · “Single data structure” vs the three-registry rule — how we reconcile

You want the hero's disparate info (the logical JSON, the UI JSON, the asset entry) connected under one data structure. The game has a hard rule the opposite way: content is authored in three registries — logical (gameplay), UI (presentation), asset (art) — linked by one id. That split exists on purpose (server-authoritative economy, reskinnable UI, the config tool).

The tension, stated plainly. Physically merging the three files into one would violate the three-registry rule (and break reskinning / server-authority). But scattering the same hero's variables across three lookups in code is exactly the “disparate information” you want gone.
The reconciliation (recommended). Keep authoring split across the three registries (rule obeyed), but resolve them once into a single cohesive HeroClass object — the one structure every consumer references. The three JSONs become authoring facets of one runtime structure, not three things code juggles. This is already half-done (content.ts builds C.HEROES; the data/heroes.js barrel merges in name/asset/portrait) — we formalize it into one named HeroClass. If you'd rather actually collapse to one file per hero, that's a real option too — but it's a deliberate break from the rule; see Q6.

1 · Template vs Instance

template HeroClass — stateless definition

One cohesive, stateless / read-only structure per playable hero — shared by every copy. Resolved from the three registries at load. This is what “dictates the loadout & holds all the info”:

HeroClass {                // id 2000 · key "knight"
  // ── identity + gameplay (logical) ──
  id, key, rarityKey, weaponChainKey,
  baseAtk, baseHp, baseDef,
  progression,                // curve (see Q4)
  normal:{chargeMs,effect}, limit:{orders,effect},
  loadout: [slotKey…],        // NEW — the slots this class has
  classKey,                   // NEW — class axis (class accessories)
  // ── presentation (UI) ──
  name, emoji, abilityNames,
  // ── look (UI + asset) ──
  asset:{ chip, portrait,     // image ref(s)
          anchor, portraitFraming, combatScale }
}

Storage stays 3-registry; this resolved object is the single structure code uses.

instance HeroInstance — stateful account item

The player's owned copy — a stateful item saved in the account items section (this already exists as Character — v5 model: “owned hero characters + gear pieces, one instance each”). It holds “all its stuff” and points at its class:

HeroInstance {           // account.items
  cid,                     // this copy's id
  classId,                // → HeroClass (was `hero`)
  level, abilityLevel,     // progression state
  ascension,               // upgrade state
  rarity,                  // rolled/ascended rarity
  // loadout STATE = gear instances
  // with equippedTo === cid (relational)
}

Dupes from gacha = multiple instances of the same class, each with its own state + equipped gear.

The connection HeroClass (template, read-only, resolved from 3 registries) ▲ classId HeroInstance (account.items — level / ascension / rarity / abilityLevel) ▲ equippedTo === cid GearItem instances (account.items — the equipped loadout, one per slot)

2 · Assets — one swappable reference on the class

How it works today. The class has one art reference (iconAssetId → e.g. hero.knight → one PNG). That single image feeds both surfaces, framed two ways: the combat chip via the asset's anchor × combat.scale, and the portrait via the UI portrait crop/zoom. So one field swaps the whole look — it's one image, framed twice, not two separate images.

Folded into HeroClass.asset, this is exactly “a simple reference for portrait + chip.” Two shapes to pick:

A · One ref, framed twice recommended

asset:{ ref:"hero.knight",     // swap here → chip + portrait
        anchor, portraitFraming, combatScale }

One swap; matches the trim-tool one-art workflow; zero duplication.

B · Split portrait + chip refs

asset:{ chipRef:"heroChip.knight",
        portraitRef:"heroPortrait.knight",
        anchor, portraitFraming, combatScale }

Independent portrait vs chip art; doubles art + framing. (Q5)

3 · The equipment slots — today

The real gap. Slots are a single global set (weapon · armor · trinket) iterated everywhere; the class does not reference its equipment, and there's no class axis.

4 · Proposed — the class declares its loadout proposed

Same primitives (key-kind slots, id-kind pieces, derived loadout, flat account). Two data moves + one runtime swap.

4.2 · The class declares its loadout + class

// game/heroes/2000.json (logical) — the class template's gameplay facet
{ ..., "slots":["weapon","hat","armor","boots","accessory","classAccessory"], "classKey":"knight" }

Literally “the class defines the list of things equipped on / acting on it.” Fully data-driven — any class can have any subset/superset of slots, in any order (drives render order). DRY alt (Q1): a gearLoadout.baseSlots singleton + per-class extras.

4.3 · The class axis — new key-kind heroClasses

“Class-specific” needs a class axis (absent today). Add key-kind heroClasses ({ key } + UI name/icon). The HeroClass references one (classKey); class-bound pieces reference one. A class may be 1 hero or a family several heroes share (Q2).

4.4 · Runtime — one selector + one gate

slotsForClass(heroClass) → heroClass.slots          // replaces the global loop
canEquip(pieceDef, heroClass, slotKey) →
     pieceDef.slot===slotKey && heroClass.slots.includes(slotKey)
  && (!slotDef(slotKey).classBound || pieceDef.classKey===heroClass.classKey)

for (const slot of C.GEAR_SLOTS) → for (const slot of slotsForClass(heroClass))
Equip flow (same pipeline, new gate, derived loadout) view → actions.equipItem(cid, gearId) → reducer: canEquip(pieceDef, class, item.slot) ? clear-that-slot-on-instance → set equippedTo=cid → persistence: flat GearItem patch → account.items

4.5 · Account — unchanged shape

  • HeroInstance = Character in account.items (rename hero→classId for clarity, optional). Loadout state = gear instances with equippedTo === cid — relational, not a per-slot map.
  • Slots live on the class template, never on the instance — every dupe shares the class's slot set, keeps its own equipped items.
  • No 7th section, no new instance field for slots; classKey read from the piece def.

5 · Architectural sense check

  • Single structure ✕ three-registry — reconciled. Authoring stays split (rule obeyed); one resolved HeroClass is the structure code references. No physical merge.
  • Template vs instance is the game's own model. Class = definition (config); instance = Character in the six-section account. We're formalizing, not inventing.
  • Typed field/ref, never a tag. slots, classKey, piece.classKey, slot.classBound are declared refs/fields — config lint-checked.
  • id-kind vs key-kind. gearSlots/heroClasses key-kind (coded); heroes/gearPieces id-kind.
  • No logic in data. Data = which slots / class-bound / which class; the rule (canEquip) is code.
  • All tuning is data. Slot sets, class bindings, loadouts, asset refs = JSON.
  • View pure reader · account server-ready. View reads the resolved class; equips via controller→reducer; loadout derived; transaction vocabulary unchanged.
  • Surgical. One selector + one gate; swap ~40 global-loop refs; formalize the existing read-model; no parallel data path.
  • New: slots, classKey, the heroClasses category, and the formalized HeroClass read-model — the only genuinely new pieces.
