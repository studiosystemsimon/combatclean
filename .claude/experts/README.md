# experts — the project's customisable expert roster

`registry.json` is the **single source of truth** for this project's *experts* — the role-based
subagents `run-changeset` routes each change to. Everything else about experts (the `EXPERTS` enum +
routing rule in `run-changeset.mjs`, the valid-roles lists in `transcript-to-changeset` /
`router/policy.md`, the roster tables in `.claude/README.md`, the governance note in `CLAUDE.md`, and
each expert's `## References` section) is **generated** from this file.

> **Do not hand-edit inside a marker region.** Anything between an `EXPERTS:*:START` and
> `EXPERTS:*:END` marker is regenerated by `manage.mjs`. Edit `registry.json`, then run `sync`.

## Commands (`manage.mjs`)

```bash
node .claude/experts/manage.mjs list            # roster: enabled/disabled, group, model, teams, refs
node .claude/experts/manage.mjs sync            # regenerate all wiring from the registry (idempotent)
node .claude/experts/manage.mjs add <spec.json> # add an expert from a JSON spec
node .claude/experts/manage.mjs disable <name>  # disable + archive its .md to experts/disabled/
node .claude/experts/manage.mjs enable  <name>  # restore a disabled expert
```

The `/add-expert` and `/disable-expert` skills are the natural-language front-ends; they build the
spec / pick the name and call this script. `sync` is idempotent — on an unchanged registry it makes
no changes.

## Registry schema

```jsonc
{
  "teams": {
    "<team-name>": {
      "description": "what this team is",
      "references": ["ARCHITECTURE.md", "src/game/README.md"]  // injected into every member's context
    }
  },
  "experts": [
    {
      "name": "engineer",              // kebab-case; matches agents/<name>.md and the subagent type
      "group": "execution",            // execution | creative | advisory | gate
      "enabled": true,                 // false = disabled (kept, .md moved to disabled/)
      "model": "sonnet",               // haiku | sonnet | opus
      "role": "Simulation & systems engineer",
      "order": 1,                      // ordering within its table / the EXPERTS array
      "owns": ["src/game/**", "..."],  // owned path globs

      // selectable experts (group execution | creative) — used for routing + tables:
      "routePriority": 5,              // first-match order in the routing rule (lower = earlier)
      "routeHint": "mostly src/game|core|app|input (or src/data/types.ts)",
      "ownsLabel": "`src/game`, `src/core`, ...",   // README "Owns" column (display)
      "focus": "Simulation logic, ...",             // README "Focus" column (display)

      // advisory experts (group advisory):
      "consultFor": "Scoping, prioritisation, ...", // README "Consult for" column
      "consultShort": "scoping / acceptance criteria",

      "responsibilities": ["...", "..."],  // the common definition every expert shares
      "teams": ["core-sim"],               // teams this expert belongs to
      "references": ["ARCHITECTURE.md"]    // extra context files injected into this expert's context
    }
  ]
}
```

**Groups.** `execution` and `creative` experts are *selectable* — they appear in the `EXPERTS` enum,
the routing rule, and the "Execution + creative" table, and `run-changeset` can route a change to
them. `advisory` experts are read-only consultants (never run in worktrees). `gate` is the `qa`
functional gate. Only `execution` / `creative` / `advisory` experts are managed by the add/disable
skills; the `qa` gate and the `arch-*` reviewer/fixer pairs are intentionally out of scope.

**Teams + references.** A team is a named group carrying a shared **reference bundle**. `sync` writes
each expert a `## References` section = its own `references` ∪ the `references` of every team it
belongs to, and `run-changeset` tells the expert to read those files before starting. Put an expert
on a team to give it that shared context; the team itself is just an entry in the `teams` map.
